# 实时问诊提醒契约（前端适配 v1）

本次实现宽幅转写、病历侧栏及转写区域内的提醒交互。**云端提醒生成及以下 PATCH 路由尚未实现**，需要后端同学接入。网页不基于关键词生成临床问题，不直接调用云端模型，不把提醒写入病历。

## 页面与同步

审核工作台改为约 65% 转写、35% 病历。来源核对按需打开侧边抽屉；“专注转写”隐藏病历区但保留未保存输入。小屏使用“问诊与提醒 / 病历审核”切换。

提醒与原文位于同一卡片，通过实时音频契约中的 `GET /api/sessions/{id}/realtime` 完整快照同步，不增加模型调用轮询。后端应在最终转写到达后合并、节流触发模型分析，返回建议追问、待确认事项及对应原句。提醒直接附在对应转写语句下方；绿色追问、橙色核实，原句同步着色。已处理提醒在原句下折叠，不设置独立提醒面板或分类页签。专注转写模式同时放大原句和问题字号。

## 可选快照扩展

在 `SessionDetail.realtime` 增加 `guidance`。省略或 null 表示未启用，页面展示空状态；不影响已有转写、保存与确认。下面仅为结构示例：

```json
{
  "guidance": {
    "revision": 4,
    "transcript_revision": 12,
    "status": "ready",
    "items": [
      {
        "id": "question-stable-id",
        "kind": "follow_up",
        "question": "不适从什么时候开始？",
        "reason": "当前对话提到不适，但起病时间尚未明确。",
        "priority": "routine",
        "status": "open",
        "anchor_segment_id": "sentence-id",
        "source_ids": ["sentence-id"]
      }
    ]
  }
}
```

| 字段 | 约定 |
| --- | --- |
| `revision` | 提醒集合版本，非负整数；内容、排序、状态任何变化递增 |
| `transcript_revision` | 本轮提醒依据的累计原文版本，必须与实时状态使用同一版本体系 |
| `status` | `waiting / updating / ready / failed`，区分等待、更新、已完成分析及失败 |
| `items[].id` | 稳定且唯一的提醒 ID；同一问题后续更新继续使用同一 ID |
| `kind` | `follow_up` 建议追问；`verify` 待确认（如含糊表述、前后不一致） |
| `question / reason` | 面向医生的简洁提问和提出依据；纯文本，不渲染 HTML |
| `priority` | `routine / important`；排序由后端给出，避免每次快照无意义跳动 |
| `status` | `open / asked / resolved / dismissed`，含义如下 |
| `anchor_segment_id` | 可选，提醒显示所依附的有效原句 ID。仅表示展示上下文，不作为证据；缺失信息型问题应明确提供此字段 |
| `source_ids` | 当前会话转写的有效证据原句 ID，可为空。未提供有效 anchor 时，前端使用 source_ids 中 seq 最大的有效原句；均不存在时只显示待关联数量，不随意附在无关句子上 |

转写版本不匹配、连接中断、模型更新或失败时，保留已有提醒但禁用状态操作，明确标注正在更新或上次提醒。未知格式仅使提醒模块不可用，不中断转写。提醒集合变化必须同时递增 `realtime.version`，防止旧快照覆盖医生刚完成的操作。

## 提醒状态操作（后端待实现）

`PATCH /api/sessions/{session_id}/realtime/guidance/{item_id}`

```json
{
  "expected_guidance_revision": 4,
  "status": "asked"
}
```

请求沿用 Cookie / CSRF，携带 `Idempotency-Key`。成功返回 200、完整一致的 `SessionDetail`，包含新 `guidance.revision` 和 `realtime.version`。前端等待成功响应才更改状态，失败保留原状态；请求超时 10 秒，后续快照可以恢复已成功但响应丢失的操作。后端同时保证重复设置同一状态无副作用。

| 状态 | 语义 |
| --- | --- |
| `open` | 待处理；也用于重新打开已处理事项 |
| `asked` | 医生已问，仍待患者回答；仍显示在建议追问中，不能当作信息已明确 |
| `resolved` | 医生标记已核实，或后端发现明确回答后解决；模型自动解决须有可追溯回答依据 |
| `dismissed` | 医生略过此项，保留历史；后续模型不能使用新 ID 重复推送同一个问题 |

前端对追问提供“标记已问”，随后允许“已核实”；待确认项直接提供“已核实”。两类均可略过，展开原句下已处理的提醒后可重新打开。**这些操作仅管理提醒，不更改原文、病历字段或原有逐字段审核状态。** 已确认病历的提醒只读。

后端原子校验会话归属、提醒归属、有效状态转换、集合版本、原文版本和病历未确认。冲突返回 409 `guidance_revision_conflict` / `guidance_stale` / `session_confirmed`；未启用返回 404 `guidance_unavailable`；服务不可用返回 503。错误正文沿用 `{code,message}`。不得用提醒接口绕过既有病历修改、确认权限。

## 模型侧对齐

- 输入来自同一会话累计的最终转写、现有提醒及处理状态；不能只看最新小片段而遗忘已回答的问题。
- 优先返回与本轮对话相关的少量问题，合并重复问题；原文修正后撤回或修正失效提醒。
- 区分“尚未提及”和“明确否认”；对不确定内容提出核实问题，不能擅自补成临床事实。
- 提醒范围为问诊补充和信息核对，不自动输出确诊、处方或未经验证的紧急程度。
- `resolved` 和 `dismissed` 项应随快照返回并在原句下折叠，不能每轮分析清空医生处理记录。
- 待确认提醒不自动阻断病历确认；现有音频收尾、草稿版本和医生逐项审核规则继续生效。

## 联调要点

验证新句到达后提醒刷新、已问但未回答仍待处理、明确回答后解决、忽略问题不重复、旧提醒不可操作、断线恢复、409 保留状态、跨患者隔离，以及提醒操作不覆盖医生正在编辑的病历。真实模型质量与延迟需另行联调；本机模拟演示不属于云端功能实现。
